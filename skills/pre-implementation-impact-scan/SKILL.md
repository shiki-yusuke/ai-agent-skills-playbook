# Pre-Implementation Impact Scan

コード変更に着手する **前** に、影響範囲を read-only で調査し、人間が着手可否を判断できる形にレポートするための skill。

この skill は**実装しない**。commit・push・PR作成・設定変更は一切行わない。コード編集も行わない。唯一の例外は、ユーザーが指定した場所への調査レポート自体の保存のみ（詳細は末尾「禁止事項」参照）。

## 既存 skill との違い

- 実装担当の subagent/skill: 実装・改修そのものを担当する。調査結果をもとにコードを書く。
- `pre-implementation-impact-scan`（this skill）: 実装に入る **前** の影響範囲調査に責務を限定する。コードは書かない。着手判断の材料だけを揃える。**コードベース全体を対象に、シンボル参照ツールでその場で動的に調べる**（事前の蓄積知識は持たない）。
- `spec-based-impact-analysis`（併用スキル）: 恒久仕様が整備済みの領域限定で、事前に書かれた仕様（閾値・不変条件・エッジケース）を参照する。役割が異なり、置き換えではなく補完関係にある（手順9参照）。

実装が必要になったら、この skill の出力を引き継いで通常の実装フローに渡す。

## いつ使うか

- 変更対象シンボル・ファイル・機能名が分かっている状態で、着手前に影響範囲を確認したいとき
- チケットの変更候補が出た直後、実装方針を固める前
- PR レビューで「この変更、他に影響ないか確認して」と指摘されたとき
- レイヤーを跨ぐ変更を検討しているとき（例: ドメイン層↔プレゼンテーション層、コアロジック↔プラグイン境界）

## 前提原則

- **read-only**: ファイル編集・commit・push・PR作成・設定変更は行わない。読み取り系ツール（シンボル参照ツール、ファイル閲覧・検索・シェル読み取り手段）のみ使う。
- **「影響なし」と断定しない**: 参照が見つからなかった場合も「現時点の探索で参照は見つからなかった（未検出の可能性あり）」と書く。ゼロ件を確定情報として扱わない。
- **AI 検出であることを明記する**: 出力の各セクションは人間の最終確認を前提とする。特に依存方向・アーキテクチャ境界の判定は、pattern 検出の限界を明記する。
- **セマンティックなシンボル参照ツールを優先する**（例: Serena の `get_symbols_overview` → `find_symbol` → `find_referencing_symbols`）。`grep`/`rg` はこれらのツールで拾いきれない文字列参照（コメント内言及、動的 import、文字列キー参照）を補完する用途に限定する。これらのツールが使えない環境では `grep`/`rg` で代替するが、精度が落ちる点に留意する。

## 手順

### 1. 調査対象を確定する

ユーザー入力から以下のいずれか（複数可）を特定する。曖昧な場合は最も具体的な粒度（シンボル > ファイル > 機能名）を優先する。

- 変更対象シンボル（関数名・クラス名・型名）
- 変更対象ファイルパス
- 機能名
- チケット番号とその変更候補
- PR レビューで指摘された箇所

### 2. シンボル探索

1. 対象ファイル/ディレクトリの構造を把握する
2. 対象シンボルの定義箇所を特定する
3. 参照元を全展開する（呼び出し元、実装先、型の利用箇所）
4. 見つかった参照元それぞれについて、アーキテクチャ上のレイヤー（例: ui / presentation / domain / infra 等、対象プロダクトの実際の層構成に合わせる）を分類する

### 3. grep/rg による補完探索

シンボル探索ツールで拾いにくいものを補完する:

- 文字列キー参照（設定キー、i18n キー、feature flag 名等）
- 動的 import / re-export 経由の参照
- テストファイル内の直接文字列マッチ（symbol 解決に乗らない mock 等）
- docs/spec 内の言及

### 4. 依存方向チェック

対象プロダクトのアーキテクチャ規約（レイヤー依存図・許可された依存方向）を確認し、以下を検証する:

- 下位レイヤー（例: ドメイン層、コアロジック）から上位レイヤー（例: プレゼンテーション層、UI層）への新規依存が増えていないか
- 変更が特定レイヤーに及ぶ場合、そのレイヤーが許可された依存方向以外（外部ライブラリ・上位レイヤー等）に依存していないか
- 逆方向依存の疑いがあれば file:line で列挙する。判定に迷うものは「要人間確認」に回す

このステップは対象プロダクトのアーキテクチャドキュメント（依存方向ルール・レイヤー定義）を前提とする。存在しない場合はこのステップをスキップし、その旨を明記する。

### 5. アーキテクチャ境界チェック（該当する場合）

対象プロダクトが Port/Adapter・プラグイン境界・モジュール境界等の明示的な境界を持つ場合:

- 境界を迂回する直接 import が新規に増えていないか
- 既存の除外ルール（レガシー例外・テスト専用等）に該当するかを区別する

### 6. サブシステム波及確認（プロダクト固有）

対象が特定の重量サブシステム（例: 外部エンジン連携、レガシーランタイム、プラグインシステム）に触れる場合、そのサブシステム固有の契約ドキュメント（ライフサイクル仕様・保存フロー仕様等）に抵触しないか確認する。プロダクトごとに具体的なチェック項目を追加する。

### 7. 国際化・プラットフォーム固有の波及確認（該当する場合）

- 文言・ローカライズファイルに触れるか（触れる場合、管轄チームの確認が必要な旨を明記）
- RTL/LTR・レイアウト反転に影響するか
- 特定プラットフォーム依存の挙動（タッチイベント・viewport 等）に触れるか

### 8. テスト・E2E・Storybook 影響の洗い出し

- 変更ファイルと同階層・同名のユニットテストを列挙する
- 変更シンボルを参照しているテストファイルを列挙する
- 関連する E2E テストを列挙し、CI 実行対象への登録が必要か判定する
- UI コンポーネントの新規作成・変更が Storybook 等のカタログ更新を要するか判定する

### 9. docs/spec 更新要否の判定

- 変更が既存の `docs/**` の記述と矛盾しないか（矛盾する場合、どの doc の更新が必要か列挙する）
- 新しい契約・仕様を追加する変更であれば、どの doc に追記すべきかを提案する
- **spec-based-impact-analysis 連携**: 対象ファイル・シンボルが `docs/spec-impact/specs/**`（または導入先で採用した配置場所）のいずれかの SPEC の `trace`（frontmatter）に一致するか、registry + 対象領域ディレクトリを確認する。一致する場合:
  - 該当 SPEC の EARS 要求・閾値・変化軸チェック・エッジケースを本レポートの「9. docs/spec 更新要否」に転記し、変更がこれらの不変条件と矛盾しないか明記する
  - 変更が恒久仕様の内容に及ぶ場合、「12. 実装に進む前の推奨アクション」に「同一PRで該当SPECファイルを更新する」旨を明記する
  - 該当領域の SPEC がまだ存在しない場合は「未整備領域」として記録するに留め、この skill 内で新規 SPEC を作成しない

## 出力フォーマット

以下の構成でレポートを出力する。保存先が必要な場合はユーザーに確認する（この skill 自体は保存先を強制しない）。

```markdown
# Impact Scan: <調査対象>

## 1. 調査対象
<シンボル/ファイル/機能名/チケット/PR指摘のいずれか、と調査時点の前提>

## 2. 変更仮説
<ユーザー入力から読み取れる変更の意図・想定スコープ。断定せず仮説として書く>

## 3. 直接影響ファイル
<変更が直接触れると想定されるファイル一覧>

## 4. 参照元一覧
<シンボル参照探索 + grep補完の結果を file:line 形式で列挙。レイヤー分類付き>

## 5. 依存方向チェック
<一方向依存の逸脱有無。逸脱疑いは file:line で明記>

## 6. アーキテクチャ境界チェック
<境界を迂回する直接参照の有無>

## 7. 影響テスト候補
<既存テストのうち影響を受けうるもの一覧>

## 8. 影響E2E / Storybook / Visual確認候補
<影響E2Eテスト、CI登録要否、カタログ更新要否>

## 9. docs/spec 更新要否
<矛盾する既存記述、追記が必要な doc の候補。spec-based-impact-analysis連携結果を含む>

## 10. リスク
<この変更が引き起こしうる回帰・副作用の仮説>

## 11. 人間確認が必要な点
<AI検出の限界により断定できない箇所。依存方向・境界判定含む>

## 12. 実装に進む前の推奨アクション
<次にどのskill/subagent/確認に進むべきかの提案>
```

## 禁止事項

- ファイル編集・commit・push・PR作成・設定変更
- 調査レポート以外のファイルの新規作成
- 「影響なし」の断定（探索の限界を必ず明記する）
