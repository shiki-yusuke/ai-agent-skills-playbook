# Procedure — 影響範囲分析の標準手順

AI エージェント（Claude / Codex）がこの手順で影響範囲分析を実行する。出力は `templates/impact-report.md` 形式で、元 Issue / PR のコメントに投稿する。

## 入力の正規化

チケット管理ツール / GitHub Issue / PR / 自由記述のいずれからでも、同じ**変更要求モデル**に正規化してから分析する:

| フィールド | 内容 |
|---|---|
| 変更種別 | 仕様変更 / 要件追加 / バグ修正 / UI変更 / 計測変更 / 権限変更 |
| 起点 | SPEC ID（あれば）または route / component / symbol / event / 既存テスト |
| 現状 / 期待 | いまの挙動と変更後の期待 |

記入漏れ・種別の複数選択は分析開始前に差し戻す。

## モード A: requirement-first（事前分析）

```text
1. 正規化      上記の変更要求モデルに整形
2. 起点特定    SPEC ID 指定があればそれ。なければ registry.md + `rg` で specs/ を検索し、
              route・component・symbol・イベント名・既存テストから起点を生成
3. 宣言収集    起点 SPEC の trace と related_specs（1 ホップ。rel 種別の意味に従って辿る）
4. 現存確認    宣言 target が現在のコードに実在するか検証（Declared → Verified）。
              消失・glob 過広は candidates に落とし、無効リンクとして報告
5. 証拠探索    @spec アノテーション・テスト内の SPEC ID・計測イベント symbol を rg。
              locator prefix はコード検索前に外すこと。
              宣言外のヒットを candidates 化
6. e2e 照合    trace 宣言された e2e の CI 登録状態を確認し、
              manual-only / nightly-only / 未登録を verification gap として報告
7. レポート    confirmed / candidates（上限 20 行）/ unknowns の 3 区分 + テスト不足 + 自己批判 1 節
8. 人間判定    元 Issue / PR コメント上で行単位に ✅承認 / ❌棄却（理由付き） / ⏸保留
```

**推奨: シンボル参照探索ツールとの併用**。手順3・5の「宣言収集」「証拠探索」は、Serena 等のセマンティックなシンボル参照グラフツール（`find_referencing_symbols` 相当）があれば `rg` より高精度に候補を洗い出せる（`rg` はキーワードが偶然一致しない限り発見できないが、シンボル参照グラフは呼び出し元を機械的に列挙できる）。「pre-implementation-impact-scan」skill と併用する場合、そちらの探索結果をこの手順の証拠源としてそのまま使ってよい。

## モード B: diff-first（PR レビュー）

```text
1. diff の変更ファイル・symbol を抽出（generated / vendored / submodule は schema.md の境界で除外）
2. @spec / trace target / テスト内 SPEC ID から触れた SPEC を逆引き
3. PR の影響宣言（三値表）と照合し、宣言漏れ・過剰宣言を提示
4. 触れた SPEC の要求 ID 単位でテスト有無を確認し、テスト不足を指摘
```

## 確信度（Declared × Verified）

| 確信度 | 条件 | 区分 |
|---|---|---|
| High | trace 宣言あり かつ 現存確認済み | confirmed |
| Medium | 宣言のみ（現存未確認）または 証拠のみ（一致するが未宣言） | candidates |
| —（推測） | 裏付けなしの意味的推測 | unknowns |

根拠 locator（`path:line` / symbol / diff hunk）のない High は禁止。リスクは severity と verification gap を独立表示する（集約スコアは作らない — 複数の観点を1つの数値に潰すと根拠が説明できなくなる）。

## 変化軸チェック（毎回照合）

対象プロダクトで実際に存在する変化軸（例: LTR/RTL・タブレット/デスクトップ・権限・構成条件[フィーチャーフラグ/環境変数/実行時ユーザーコンテキスト]）。イベントの「意味変化」（名前は同じで解釈が変わる）とデータ後方互換も必ず一度疑う。

## モデル委譲の I/O 契約（複数モデルを使い分ける場合）

委譲は責務で固定する（モデル名・グレードは目安。使える環境に合わせて読み替える）:

| 責務 | 目安 | 入力 | 出力 | 禁止事項 |
|---|---|---|---|---|
| 抽出・正規化・重複除去（trace 展開、検索と整形、テスト有無、schema/ID 検証） | 軽量モデル | 対象パス・検索パターン | JSON（locator 付きヒット一覧） | 確信度の付与・行の削除 |
| 起点選択・関係探索・candidates 一次整理・レポートドラフト | 中位モデル | 変更要求モデル + 起点 SPEC | 区分未確定の候補表 | confirmed への昇格判断 |
| 証拠検証（Verified 判定）・確信度確定・レポート確定 | 主エージェント | 上記の出力 | 最終レポート | 委譲不可 |
| 敵対的レビュー | 高性能モデル | レポート + 起点 SPEC | templates/codex-review-request.md 参照 | 常時実行しない（severity=High / unknowns 残存 / パイロット評価時のみ。コスト管理のため） |

## チケット管理ワークフローとの接続（例: フェーズ制の変更管理ツールを使う場合）

Intent → Spec → Implement → Verify → Done のようなフェーズ制ワークフローを使っている場合の接続例:

- **要求定義フェーズ**: 変更要求に「関連恒久 SPEC = ID / 新規候補 / なし（根拠付き）」を宣言する
- **実装フェーズ**: 恒久要求が変わる場合だけ、同一 PR で `specs/` を更新する
- **検証フェーズ**: モード B（diff-first）で宣言と照合する
- **完了フェーズ**: 反映済みかの監査のみ
- 昇格規則: merge 後も維持される現行挙動の定義のみ恒久 SPEC に昇格させる。調査手順・一時的な実装範囲・証拠収集手順は昇格させない
- 注意: チケット管理ツール側の状態フィールド（例: ワークフロー状態）は、完了後も古い状態のまま残ることがある。state フィールドだけで「現在も有効な仕様」と判定しない
